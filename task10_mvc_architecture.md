# Задание 10 (средняя сложность). Архитектура MVC

## Приложение

Рассмотрим настольное приложение «Библиотека»: пользователь добавляет
книги, редактирует сведения, удаляет записи и ищет книги по автору.
MVC разделяет приложение на три независимые части: Model, View и
Controller.

```text
       действие пользователя
              |
              v
+----------+  вызов метода  +------------+  изменение  +-------+
|   View   | -------------> | Controller | ----------> | Model |
| (окно)   |                | (сценарий) |             |(данные)|
+----------+                +------------+             +-------+
      ^                                                     |
      |                результат / уведомление              |
      +-----------------------------------------------------+
```

## Model — модель

Модель хранит состояние и реализует предметные правила. В «Библиотеке»
это классы `Book` и `Library`, а также слой сохранения в SQLite.

- `Book`: название, автор, год, идентификатор;
- `Library`: получение списка, добавление, изменение и удаление книг;
- проверка года и обязательных полей;
- транзакции и запросы к базе данных.

Модель ничего не знает о кнопках, окнах и расположении элементов. Она
не вызывает методы интерфейса и поэтому может тестироваться отдельно.

## View — представление

Представление отображает данные и передаёт действия пользователя
контроллеру. Для «Библиотеки» это главное окно, таблица книг, поля
поиска, форма редактирования и диалоги ошибок.

- формирует экран по данным модели;
- преобразует нажатия кнопок в вызовы контроллера;
- не выполняет SQL-запросы;
- не принимает предметных решений, например не определяет допустимый год.

При смене GUI с Tkinter на Web-интерфейс модель меняться не должна.

## Controller — контроллер

Контроллер координирует сценарий между представлением и моделью.

1. Получает от View событие «Добавить книгу».
2. Проверяет полноту введённых данных и преобразует их к нужным типам.
3. Вызывает `Library.add_book(...)`.
4. Передаёт View обновлённый список либо сообщение об ошибке.

Контроллер не рисует окно и не хранит записи базы внутри себя.

## Пример полного сценария

Пользователь вводит «Чистый код», «Роберт Мартин», `2008` и нажимает
«Добавить». View вызывает `controller.add_book(form_data)`. Контроллер
преобразует год в `int` и вызывает модель. Модель проверяет правила,
делает параметризованный `INSERT`, фиксирует транзакцию и возвращает
книгу с `id`. Контроллер просит View показать новую строку и очистить
форму. При ошибке модель не меняет состояние, а View получает текст
ошибки без SQL и технических деталей.

## Преимущества и проверяемость

- **Model** проверяется unit-тестами без графического интерфейса.
- **Controller** проверяется с подменной моделью: тест видит, какой
  метод был вызван и какой результат возвращён представлению.
- **View** проверяется отдельно на отображение готовых данных.

Такое разделение уменьшает связанность: база, интерфейс и сценарии могут
изменяться независимо. Один и тот же контроллер и модель можно использовать
для настольного окна, REST API или CLI.
